# Wireshark Validation: HTTP vs HTTPS

## Objective

Observe traffic generated by the local Mobile App and API Security
project and compare HTTP with HTTPS/TLS.

## Test Environment

- Capture interface: Adapter for loopback traffic capture
- Local API address: 127.0.0.1
- HTTP port: 3000
- HTTPS port: 3443
- Test endpoint: /api/health
- Tool: Wireshark

Only traffic generated by the local application was used for this
observation.

## HTTP Observation

**Display filter:** `tcp.port == 3000`

The capture showed a TCP connection to port 3000, followed by a
readable HTTP request:

`GET /api/health HTTP/1.1`

The corresponding response was `HTTP/1.1 200 OK`, with JSON
content from the local health endpoint.

This demonstrates that Wireshark can identify the HTTP request
and response and inspect application-level content when it is
sent over unencrypted HTTP.

## HTTPS Observation

**Display filter:** `tcp.port == 3443`

The capture showed a TLS handshake, including a Client Hello and
Server Hello, followed by TLS application-data packets.

The health endpoint returned `HTTP/1.1 200 OK` when tested with
curl using the local development certificate.

The packet list did not display the HTTP request path as readable
HTTP content in the captured TLS application-data packets.

This observation is consistent with TLS protecting application
content while connection metadata remains observable.

## Comparison

| Observation                               | HTTP        | HTTPS/TLS                                           |
| ----------------------------------------- | ----------- | --------------------------------------------------- |
| TCP connection visible                    | Yes         | Yes                                                 |
| HTTP request path readable in packet list | Yes         | Not in the observed TLS application data            |
| Response status verified                  | HTTP 200 OK | HTTP 200 OK                                         |
| TLS handshake visible                     | No          | Yes                                                 |
| Application content protected in transit  | No          | Yes, when TLS is correctly configured and validated |

## Limitations

The HTTPS server uses a self-signed certificate for local testing.
The curl HTTPS test used `-k`, which bypasses certificate
validation. Therefore, the test confirms that the HTTPS endpoint
responded over TLS, but it does not establish that the certificate
is trusted by clients.

The capture was limited to local loopback traffic and the project's
own API. It does not demonstrate the behaviour of a deployed mobile
application or prove every authentication and authorisation control.
